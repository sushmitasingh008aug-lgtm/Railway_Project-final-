3 Detailed Gap Analysis — What We Are Doing Wrong

GAP-1 · No combined multi-department blocks (the PS's central ask) CRITICAL

Real IR practice: one night corridor block where Engineering tamps track, Traction fixes the OHE, and S&T services point machines — simultaneously, in the same window. One disruption, three departments served. Our CP-SAT model schedules each task as an independent interval; nothing encourages co-timing. Three separate blocks = three traffic disruptions instead of one — exactly the inefficiency ("decentralized… poor coordination… inefficient block utilization") the PS was written to solve.

engine/optimizer_core.py — objective (§7) has zero cross-task coupling terms

GAP-2 · Single fixed horizon — no weekly/monthly planning HIGH

The PS explicitly demands plans over multiple horizons. We hard-code 7 days and even bake the literal date 2026-08-23 into Python, SQL WHERE clauses, and the Go API. A monthly run is impossible today without editing source files.

optimizer_core.py:19,39 · priority_engine.py:30 · main.go:425 · transform_and_seed.py:91

GAP-3 · Every train is an equal, immovable wall HIGH

Operationally false in two ways. First, hierarchy: a Rajdhani/Vande Bharat is sacrosanct; a mail express matters more than a MEMU; freight can generally wait. Second, elasticity: goods trains are forecast input (per the PS), not fixed truth — a critical block can legitimately absorb a short freight hold. Our model treats all 693 movements as identical hard constraints, which both over-constrains the solver and ignores the PS's "goods trains forecast" framing.

optimizer_core.py:84–96 — AddNoOverlap mixes task intervals with ALL trains uniformly; train_type fetched (line 37) but never read

GAP-4 · No traction-aware blocking MEDIUM

An OHE dropper replacement does not stop a diesel locomotive — it passes through (often at restricted speed). Only electric traction is affected. Today an OHE job freezes the whole corridor including diesels, inflating apparent "impact on train operations" and understating how much maintenance we could safely schedule. Track/S&T works, by contrast, correctly block everything.

schema.sql — no traction column on train_movements; no traffic_impact on maintenance_tasks

GAP-5 · "AI/ML" branding vs rule-based reality POSITIONING

Judges will probe the word "AI". Our priority engine is deterministic weighted scoring — genuinely defensible as explainable AI, and arguably what IR operations would trust. Do not bolt on fake ML. Recommended line: explainable rule engine now + concrete upgrade path (e.g., failure-risk prediction trained on Track Recording Car defect history feeding the same score field).

4 Corrective Roadmap (Engine + API focus)

A

Schema & Seed Data

  • train_movements: add priority_class ('Premium' | 'Passenger' | 'Freight') and traction ('Electric' | 'Diesel')
  • maintenance_tasks: add traffic_impact ('All' | 'Electric_Only') derived from task_type — OHE jobs ⇒ Electric_Only
  • Re-seed with realistic mix: ~5% Premium, ~25% Passenger/MEMU, ~35% Freight, ~70/30 electric-diesel split
  • Remove hardcoded dates everywhere; derive base time from current date at runtime
B

CP-SAT Optimizer Upgrades

  • Diesel pass-through: exclude diesel trains from conflicts with Electric_Only blocks
  • Freight elasticity: freight intervals shiftable up to ~30 min hold, penalized in objective (matches "goods train forecast" being soft input); Premium/Passenger remain hard walls with extra buffer around Premium
  • Combined blocks: bonus term rewarding same-section tasks from ≥2 different departments starting together — one disruption, multiple departments (modeled via same-start reification in CP-SAT)
  • New objective: max Σ scheduled priority + λ·combined-block bonuses − μ·freight-hold penalties
  • Horizon parameterization: accept horizon_days = 7 or 30 cleanly
C

Go API

  • /api/schedule/generate?horizon_days=7|30; remove hardcoded dates from priority/urgency math
  • /api/impact mirrors traction + class rules; new stats: combined blocks formed, diesel services unaffected through OHE works, delay split Premium / Passenger / Freight
  • Update main_test.go for the new evaluation logic
D

Validation Suite

  • No Premium or Passenger train ever collides with a block (hard invariant)
  • Diesel never blocked by an Electric_Only block
  • Freight holds never exceed the configured limit
  • Combined blocks contain ≥2 distinct departments with aligned start times
